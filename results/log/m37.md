# M37 — the answer-only state bottleneck: no trajectory-free learning; and a rollout control that CORRECTS M36

**WHY.** M36e showed the mixer's transferable CA step needs DENSE trajectory supervision; with the
final state only (depth curriculum or progressive loss) it learns nothing transferable. Diagnosis
going in: the default loop can bypass its own state — it re-reads the input every step (recall) and
carries a free latent z — so nothing forces step i of a deep run to do one CA step's job. M37 closes
that bypass and asks whether final-state labels then suffice ("idea 1" of the post-M36e brainstorm).

**Substrate (commit `3870799`).** New opt-in `state_bottleneck` for `trm_mixer` ("none" default ⇒
construction and forward unchanged; same parameters in all modes). Each step sees only the decoded
current state s_t in the input slot (the input sets s_0 only), the learned per-cell z0 every step (no
latent carry), and a zero answer slot — a Markov map on the observable state. "soft" passes
P(cell=1); "hard" passes 0/1 with a straight-through gradient. Requires cell_dim 1 and binary cells.
Tests (`tests/test_state_bottleneck.py`): default identity, parameter identity, the Markov restart
property (restarting from the decoded state reproduces later steps exactly), gradient flow, shape
guards. Also `ds_stride` from M36e is used here to mean "final state only" (stride 8, T ≤ 8).

## M37a / M37b — final state only, no depth-1 labels: every bottleneck arm collapses

Configs `configs/experiments/m37a_bottleneck_curriculum.yaml` (T ~ U{4..8}) and
`m37b_bottleneck_single_depth.yaml` (T = 4 only); records `results/m37a_bottleneck_curriculum_
20261024T145437*`, `results/m37b_bottleneck_single_depth_20261024T150059*` (RTX 2070, 9.1 / 6.4 min,
8 seeds, all arms 16,058 params except ff 16,103).

Every state-bottleneck arm (soft, hard, AND the hard arm given every intermediate state) predicts the
majority class: accuracy equals each seed's majority baseline at every T (e.g. M37a T=8: 0.541 for
soft, hard and baseline alike), EM 0, and soft/hard are bit-identical per seed. Their nominal "wins"
over `mixer_finalonly` at T ≥ 16 (+0.04–0.06, 8/0) are the majority class beating a below-chance
mixer — not a result. The default mixer arms reproduce M36e (stride 1 learns; final-only fails).
**So these configs did not test the hypothesis: the bottlenecked loop never trained.**

## Diagnostics — why it collapsed (exploratory, 1–2 seeds)

`experiments/m37_diagnostics/deep_only_and_final_only.py` (hard bottleneck, rule 110, w=24, 100 epochs
unless noted; accuracy of the free-running loop against s_1 … s_8 on 1,000 held-out rows).

| training labels (hard bottleneck) | seeds | acc at s_1 / s_4 / s_8 |
|---|---|---|
| one-step pairs only (T=1), 60 epochs | 0 | 1.000 / 0.999 / 0.996 |
| (same, DEFAULT mixer) | 0 | 1.000 / 0.459 / 0.456 |

| every state, T ~ U{4..8} | 0, 1 | ≈0.60 / ≈0.55 / ≈0.54 |

Reading: the bottleneck makes a learned step reusable by construction, but gradients through several
hard-composed steps from a random init carry almost no signal — the loop only trains when shallow
(especially one-step) labels dominate. **Final-state-only training stays at chance even with depth-1
batches mixed in.** Idea 1 does NOT give trajectory-free learning.

## M37c — one-step pairs only, then iterate to T=32 (8 seeds) — and the control that deflates it

Config `configs/experiments/m37c_bottleneck_one_step.yaml`; record
`results/m37c_bottleneck_one_step_20261024T150918*` (1.5 min). Every arm trained on (s0, s1) only.

At depth 1 the hard, soft and default mixer are the SAME computation, so they train into identical
weights (all T=1 metrics tie exactly, 0/0). M37c therefore compares ways of ITERATING one trained
step. Diagonal R' = T, accuracy / EM:

| T | `mixer_hard` (feed back 0/1 state) | `mixer_soft` | `mixer` (recall + latent carry) | `ff_matched` one-shot | **ff rolled out** |
|---|---|---|---|---|---|
| 1 | 1.000 / 0.997 | 1.000 / 0.997 | 1.000 / 0.997 | 1.000 / 0.999 | 1.000 / 0.999 |
| 8 | 0.997 / 0.977 | 0.996 / 0.972 | 0.459 / 0 | 0.564 / 0 | 0.995 / 0.971 |
| 16 | 0.990 / 0.957 | 0.987 / 0.946 | 0.446 / 0 | 0.519 / 0 | 0.988 / 0.956 |
| 32 | 0.975 / 0.928 | 0.968 / 0.909 | 0.440 / 0 | 0.516 / 0 | **0.976 / 0.934** |

"ff rolled out" = `ff_matched`, same labels / budget / recipe, iterated autoregressively
x_{t+1} = argmax(ff(x_t)) — `experiments/m37_diagnostics/ff_rollout_control.py`, run record
`results/m37c_ff_rollout_control_20261024T151032.json` (8 seeds, same seed offsets as the runner).

**Reading.**
- Feeding the decoded state back extrapolates (8/0 vs the default mixer's iteration, which falls
  below chance — it was never trained to consume its own latent), hard ≥ soft by a hair (+0.007 at
  T=32, 8/0).
- **But a plain MLP rolled out the same way does exactly as well** (0.976 / 0.934 vs 0.975 / 0.928 at
  T=32; cross-script, not paired). The bottleneck adds nothing over "predict one step, feed it back":
  given one-step labels, ANY accurate one-step predictor extrapolates by autoregression on this
  task, because the CA is Markov in the observable state and the per-cell one-step error is ~0.1%.

## ★ What this CORRECTS in M36

M36b/M36c's step-aligned supervision contains the one-step pairs (s0, s1) in every batch. The ff
rollout control uses a strict SUBSET of those labels and reaches acc 0.976 / EM 0.934 at T=32 — ABOVE
M36c's tied mixer (0.899 / 0.690). So the M36 headline "first transferable step operator in the repo"
is not a loop capability over a control: once the trajectory is supplied, the problem reduces to
learning a one-step map, which an MLP does perfectly, and autoregressive rollout does the
extrapolation. (Cross-run comparison — different training protocol and arms — but the gap is large
and in the control's favour.)

What survives of M36, at honest scope:
- The tied mixer DOES internalise the step under step-aligned supervision (it extrapolates by its own
  recurrence, with latent carry and recall), where the flat loop and final-state DS do not.
- M36c's tying contrast (tied > budget-matched and 7.3× untied mixer at T=8 in distribution) is a
  within-architecture result and stands within its scope.
- M36e's conclusion (dense trajectory supervision is required for the LOOP to learn the step) stands
  and is now joined by M37: no tested route gets a step from final-state labels.

## What this changes

- §11.2 #22's "first transferable step operator" headline is CORRECTED: depth extrapolation on
  `iterated` given step labels is matched by an MLP one-step rollout; it is not evidence for the loop.
- Trajectory-free learning of the step: still not achieved (M36e + M37). The state bottleneck is
  closed as a route (it trains only when shallow labels dominate).
- Methodological lesson for any future extrapolation claim: include an AUTOREGRESSIVE ROLLOUT control
  — the best one-step predictor available from the same labels, iterated on its own outputs.
