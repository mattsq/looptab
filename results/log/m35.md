# M35 — GPU speed substrate: real-hardware verification of a CPU-built speedup layer

## 0. Provenance and scope

The M35 code (DS-family `amp`/`cuda_graph` capture, `amp`+`cuda_graph` composition,
`cuda_graph_tail`, `train.speed: auto`, per-batch sync removal, on-device eval collection —
see CLAUDE.md §11.1) arrived in this repo's working tree pre-written and CPU-correctness-tested,
but **never run on a GPU** — it was built in a CPU-only container. This narrative is the
GPU-verification pass: fix what breaks, measure what the CPU pass could only hypothesize about,
and turn §11.3's "unmeasured, treat as hypotheses" caveat into a real §11.2 entry. All runs are
on this repo's usual dev box (RTX 2070, 8GB, Turing, fp16 tensor cores only — see the global
CLAUDE.md hardware note). No scientific (§11.2 research) claim changes here — like `infra-2.md`,
this is a perf/correctness narrative, not a new milestone result.

## 1. A real bug, found by the first real GPU test run

`pytest -q` on this box: **357 passed, 1 failed** on the untouched M35 tree (up from "skipped"
on CPU, since the CUDA-marked tests finally executed for real). The failure:
`TestDeepSupervisionGraphsOnGPU::test_ds_graph_with_amp_and_ema` — `train_deep_supervision`
under `amp=True, cuda_graph=True` raised a non-finite-epoch-loss error at epoch 1.

Isolated before touching anything:
- **Not EMA-specific** — fails identically with `ema_decay=None`.
- **Not a graph-mechanics bug** — eager AMP (dynamic `GradScaler`, no capture) on the identical
  config trains cleanly for all 12 epochs, descending smoothly, no overflow.
- **It's the default static loss scale.** Binary-searched `amp_static_loss_scale` on the DS
  multi-pass path (`n_sup=3`, `carry=True`, `hidden_dim=16`, `n_steps=3`): 32768 trains cleanly
  and matches the eager trajectory; the shipped default of 65536 overflows fp16 gradients every
  time. The single-pass standard path (`test_amp_plus_cuda_graph_trains`, same 65536 default) was
  fine — this is a DS-family-specific numerical margin issue, not a universal one.

**Fix:** lowered the default `amp_static_loss_scale` from 65536.0 (GradScaler's usual init value,
never actually run on a GPU before this) to **8192.0** — an 8x margin below the observed failure
point, comfortably below the last-known-good 32768. Updated in `src/looptab/train/loop.py`
(6 call-site defaults) and `src/looptab/config.py` (`TrainConfig.amp_static_loss_scale`), plus the
CLAUDE.md §11.1 M35 paragraph. `pytest -q` after the fix: **358 passed, 6 skipped** (the 6 skips
are the pre-existing, unrelated `trm_mixer_fused` extension tests that need the MSVC toolchain —
not part of M35). The overflow-detection test itself (`amp_static_loss_scale=1e30`, deliberately
absurd) still raises correctly — the fix only moved the *safe* default, not the overflow check.

## 2. DS-family capture — the main new lever, GPU-measured

Config: `m18e_compute_matched` (converge rule=78 w=24, 3 arms × 8 seeds, `hidden_dim=64`,
`n_steps=6`; `trm_nsup`/`trm_nsup_nocarry` are the `n_sup=4` DS-family arms this lever targets),
device switched to `cuda`, `parallel_workers: 4` (kept — §11.1 says GPU workers still help; this
config is small enough that the CUDA-context-per-worker cost is proportionally larger than on
M23's sweep, so treat these wall-clock numbers as this-config-specific, not a general
`parallel_workers` re-measurement).

| mode | wall clock (8 seeds) | vs eager | Δ(trm_nsup−trm_nods) acc | Δ EM |
|---|---|---|---|---|
| eager (GPU) | 4m31s | 1.00x | +0.0211 ± 0.0054 | +0.272 ± 0.055 |
| `cuda_graph` | 2m00s | **2.25x** | +0.0232 ± 0.0067 | +0.292 ± 0.070 |
| `amp` | 5m45s | **0.78x (slower)** | +0.0231 ± 0.0044 | +0.289 ± 0.046 |
| `amp`+`cuda_graph` | 2m09s | **2.11x** | +0.0234 ± 0.0064 | +0.296 ± 0.066 |
| CPU reference (committed M18e, `m18e_compute_matched_20260625T072348`) | — | — | +0.0236 ± 0.0026 | +0.295 ± 0.023 |

All five numbers (four GPU modes + the pre-existing committed CPU run) agree well within seed
noise — genuine correctness confirmation of the new DS-family capture path, not just "ran without
crashing." Three real findings:

1. **`cuda_graph` alone is a real 2.25x win here** — the shape (`n_sup=4` passes × small cells)
   is exactly the launch-bound regime #16 predicts graphs help.
2. **`amp` alone is a real loss (0.78x)** on this shape — consistent with the repo's established
   "small GEMMs lose under AMP" pattern (§11.3: sudoku 1.18x, ETTh1 0.74x, yeast 0.65x). This
   config's GEMMs (`hidden_dim=64`, `batch=256`, `w=24` cells) are in the small-GEMM band.
   `train.speed: auto` exists precisely because this sign is not predictable from the config
   alone without measuring — see §3.
3. **`amp`+`cuda_graph` composition is real and correctly implemented**: 2m09s ≈ the `cuda_graph`
   number, not the `amp` one — the static-loss-scale capture absorbs amp's per-step host-side
   overhead into the replayed graph rather than inheriting amp's standalone GEMM-bound penalty.
   This is the first time these two knobs have run together on real hardware (they were mutually
   exclusive before M35).

`cuda_graph_tail` (same config, `cuda_graph: true, cuda_graph_tail: true`; `n_train=4000,
batch_size=256` gives a genuine 160-row ragged tail, 4% of each epoch, not the negligible case the
doc's own `_small_loader` example describes): **2m00.6s — no measurable overhead** over plain
`cuda_graph` (2m00.1s), and `trm_nods` accuracy ticked up (0.9668 vs 0.9654) in the direction
expected from training on the recovered rows. Real, cheap, and correct on an actual config, not
just the unit-test shape.

**Not run this pass:** the ACT config row (`m23_sudoku_act_sweep`, `docs/GPU_BENCHMARK.md` §2a's
bonus row) — the other two checklist items below (§2b sync removal, and the DS-family-at-scale
question) were run instead, as the higher-value follow-ups.

### 2b. Sync removal, isolated (`git stash` A/B against the pre-M35 commit)

`m18e_compute_matched`, eager mode, same seeds, config, and hardware — only the code differs
(pre-M35 commit `e5fb887` vs. the M35 tree). Isolated with a scoped `git stash push -u -- <the
8 M35-changed files>`, leaving `scratchpad/` untouched, then `git stash pop` to restore (verified
after: identical `git diff --stat`, full suite still 358/358).

| tree | wall clock (8 seeds) |
|---|---|
| pre-M35 (`.item()` per pass) | 4m38.8s |
| M35 (on-device float64 accumulation, synced once/epoch) | 4m30.9s |

**~3% real win**, and accuracy is bit-identical between the two trees (`trm_nods` 0.9668±0.0043,
`trm_nsup` 0.9879±0.0039, `trm_nsup_nocarry` 0.9897±0.0020 — matching to 4dp) — expected, since
sync removal only changes how the *diagnostic* epoch-loss scalar is accumulated, not any tensor
math the model or optimizer touches. Small because this config (`hidden_dim=64`) isn't as
launch-bound as the shapes #16 profiled; the doc's own framing ("may be ~0 on compute-bound
configs, that is the expected and reportable answer") was the right expectation to hold — this is
a small-but-real win rather than a large or a null one.

### DS-family capture at electricity-scale width — the definitive answer to §11.3's open hypothesis

§3b's `electricity` check exercised the *standard* path at real widths, not DS-family capture —
electricity's arms don't set `n_sup>1`, and `n_sup>1` is in fact **structurally blocked for
regression tasks entirely** (`run.py` raises: "regression ... supports only standard train
path"). So the open question from §11.3 ("DS-family graphs should hurt at electricity/traffic
scale, same memory-pool competition as #18") could not be tested via any real config — it required
a direct micro-benchmark.

Two proxies were tried. The first (`bench_dsfamily_h1110.py`: flat `TRM`, `hidden_dim=1110`, but
a synthetic `converge` task's tiny `in_features=32`) showed no OOM and no meaningful slowdown —
but this was misleading: electricity's real memory pressure comes from the **huge `M×lookback`
input layer** (321×96 = 30816 `in_features`), which the synthetic task's 32-dim input doesn't
replicate. It was also the wrong architecture — electricity's actual `h1110` arms are `TRMMixer`
(per-cell, token-mixing), not flat `TRM`; a flat dense `in_features(30816)→hidden(1110)` layer is
never built in the real recipe (exactly why the committed config keeps flat `trm`/`ff_matched` at
`hidden_dim=64`, not 1110).

The faithful version (`bench_dsfamily_h1110_mixer.py`): real `TRMMixer` class, real
`in_features=30816`, `out_features=321`, `hidden_dim=1110`, `token_hidden=8`, `n_steps=8` — with
`n_sup=4, carry=True` DS-family capture bolted on directly via `train_deep_supervision` (bypassing
`run.py`'s regression guard; labels are random since this measures architecture/shape cost, not a
training result):

| mode | per-pass time | peak GPU memory |
|---|---|---|
| eager | 7.58s | **11.37GB** (already exceeds the 8GB card — WDDM shared-memory spill) |
| `cuda_graph` (DS-family, two graphs) | 20.93s | **11.99GB** |

**Confirmed, decisively: DS-family capture at electricity-scale width is harmful, matching (and
if anything sharper than) #18's standard-path finding** — `cuda_graph` is **2.76x slower**, not
faster, and uses more memory on top of an already-overflowing eager baseline. This also explains
why the committed real recipe needs `microbatch_size=64` even in eager mode at this shape — full
`batch_size=128` eager alone already exceeds 8GB. §11.3's open hypothesis is now a closed,
measured result: never combine `cuda_graph` with a wide (`hidden_dim`~1000+), high-`in_features`
`TRMMixer`/DS-family arm — not even without the graph doubling, since eager alone is already at
the memory ceiling there.

## 3. `train.speed: auto` — correctness confirmed, reseed confirmed, one real limitation found

Ran `m18e_compute_matched` with `speed: auto`, `parallel_workers: 1` (clean per-arm timing
signal, no cross-process GPU contention).

- **Picks the right mode.** For `trm_nods` (the one standard-path arm in this config — see below
  for why the other two aren't eligible), every one of 8 seeds chose `cuda_graph`
  (`eager≈0.24s | amp≈0.30s | cuda_graph≈0.105s (best) | amp+cuda_graph≈0.12s`) — exactly the §2
  manual-sweep winner.
- **Reseed is exact, not just close.** Per-seed `trm_nods` accuracy under `auto` matches the
  manual `cuda_graph` run to 3dp on all 8 seeds (e.g. seed0: 0.966/0.966, seed7: 0.957/0.957).
  Per-seed `trm_nsup`/`trm_nsup_nocarry` accuracy under `auto` matches the manual **eager** run to
  3dp on all 8 seeds (they fall back to eager — see next point). Autotune probing genuinely does
  not leak into the real run's RNG stream.
- **Real limitation, not a bug: DS-family arms get NO autotuning under `speed: auto`.**
  `trm_nsup`/`trm_nsup_nocarry` (`n_sup=4`) are exactly the arms §2 shows benefit most from
  `cuda_graph` (2.25x), but `_autotune_speed_mode` only probes through the standard-path `train()`
  call, so any arm with `n_sup>1` / `use_act` / a curriculum / `train_stable` falls straight
  through to the configured flags — here, the config's defaults (`amp=False, cuda_graph=False`),
  i.e. **plain eager**, silently. The run record labels this honestly
  (`speed_mode: "eager (auto n/a here)"`), so it's discoverable, but it means **on a config whose
  interesting arms are DS-family, `speed: auto` currently buys nothing** — the exact opposite of
  what someone reaching for "the main new lever" would expect. Worth a CLAUDE.md callout (added
  below) so nobody assumes `speed: auto` covers the DS-family win automatically.

### 3b. `speed: auto` at real scale (`electricity`, M=321) — correct, but the probe overhead can dominate

Ran the committed `m34_electricity_h24` config (7 arms, 4 seeds, widths up to `hidden_dim=1110`)
with `speed: auto` added. Two of seven arms (`trm_mixer`, `trm_mixer_nomix`, the `h1110`
microbatched arms) are excluded from autotuning by the existing `microbatch_size`-present guard
and fall back to the committed recipe (`amp=true`, no graph) — unchanged, so this run does **not**
directly test "DS-family graphs at electricity scale" (these arms don't set `n_sup>1` — the
config's `deep_supervision: true` is the per-step-readout flag on a single forward pass, not the
`n_sup` multi-pass DS-family routine — so that specific §11.3-hypothesis (a) claim remains
untested pending a config that actually combines `n_sup>1` with electricity-scale widths).

The other five arms (`hidden_dim` 44–340) *were* auto-probed, and the autotuner behaved sensibly:
it never picked plain `cuda_graph` for the two `h340` arms (probed timings show it losing to
`amp`/`amp+cuda_graph` there — e.g. one seed: `eager=20.1s | amp=14.2s | cuda_graph=32.7s |
amp+cuda_graph=16.4s`, correctly avoided), while the two small arms (`h44`, `h64`) picked
`cuda_graph`/`amp+cuda_graph` — the small/launch-bound regime §16 predicts. No candidate ever
registered as unavailable/OOM at these widths (the true #18 danger zone, `h1110`, was never
exposed to the autotuner by design).

**Numerically, every headline Δ reproduced the committed baseline within noise**, even though
several arms trained under a *different* mode than the baseline's uniform `amp`-only recipe:

| delta | committed baseline (uniform `amp`) | this run (`speed: auto`, mixed modes) |
|---|---|---|
| Δ(trm_mixer−trm_mixer_nomix) accuracy | +0.02710 ± 0.00341 | +0.02710 ± 0.00341 (identical — both fall back to the same recipe) |
| Δ(trm_mixer−ff_matched) accuracy | +0.11974 ± 0.02687 | +0.12149 ± 0.02275 |
| Δ(trm_flat−ff_matched) accuracy | +0.03074 ± 0.02287 | +0.03166 ± 0.01928 |

(all 4 metrics × all 9 configured deltas checked, not just these three — same pattern throughout.)

**But wall clock was 78m42s vs. ~16 minutes for the original recipe — roughly 5x SLOWER
overall.** The autotune probe cost (5 arms × 4 candidates × ~3 timed epochs × 4 seeds ≈ 240 extra
probe-epochs, several of them at real hidden widths up to 340) dwarfs whatever the chosen modes
saved over the 15 real epochs/arm/seed. This is exactly the risk `docs/GPU_BENCHMARK.md` itself
named ("time the probe overhead — on a short config it could exceed what it saves") — now
confirmed for real, and worse than "short config": here it's a *large* config where the probe
overhead is still the dominant cost. **Practical read: `speed: auto` is a correct exploration
tool for finding the winning mode, not something to leave on for a real run at this scale — pin
the winner manually once found**, exactly as the code's own docstring already recommends, now
with a concrete number behind the recommendation.

## 4. Net assessment

M35's mechanisms are now GPU-verified, not just CPU-correctness-tested:

- DS-family `amp`/`cuda_graph` capture: **real 2.1–2.25x win**, numerically correct.
- `amp`+`cuda_graph` composition: **real and correctly implemented**, rides the graph win rather
  than inheriting amp's small-GEMM penalty.
- `cuda_graph_tail`: **correct, free, and recovers real rows** (4% of an epoch here).
- `speed: auto`: **picks correctly and reseeds exactly** for the arms it can see, but **silently
  skips DS-family arms** (a real gap, not a crash) and **its probe overhead can make a large
  config's total wall-clock much worse**, not better — measure before leaving it on.
- One real bug found and fixed: the shipped `amp_static_loss_scale` default overflowed on the
  DS-family shape; now 8192, GPU-verified safe on both the small M18e shape and (implicitly, via
  the `amp` result in §2 not needing the scale at all since no graph was combined there) unaffected
  standard-path configs.

- Sync removal: **real, ~3% on this shape**, bit-identical accuracy (pure plumbing, as
  documented) — small because this config isn't as launch-bound as #16's shapes; matches the
  doc's own expectation.
- DS-family capture at electricity-scale width: **decisively confirmed harmful** — 2.76x slower
  under `cuda_graph`, and eager alone already exceeds the 8GB card at this shape. §11.3's open
  hypothesis is now closed.

`speed: auto` downgraded from "the main new lever's autotuner" to "not recommended for a real
run" (§11.1/config.py docstring updated) — its own probe overhead and its blind spot on DS-family
arms make manual pinning, using the dispatch rules above, the better choice going forward.

Not yet done: the `m23_sudoku_act_sweep` ACT row (low priority — #16 already established
`cuda_graph` is inert at sudoku's compute-bound scale, so this would mostly be a completeness
check on the ACT-specific halt-loss capture path, not a new speed finding).
