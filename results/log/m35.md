# M35 — GPU speed substrate: real-hardware verification of a CPU-built speedup layer

## POST-REVIEW CORRECTION (Codex, 2026-08-17) — five implementation/audit defects fixed

An adversarial review reproduced one correctness failure and found four audit/benchmark defects.
This block supersedes the affected claims later in this historical narrative; the original text is
left below so the provenance of the correction remains visible.

1. **Static-AMP overflow detection missed the final optimizer step (fixed).** The old check looked
   only at the pre-update epoch loss. A one-batch/one-epoch reproduction returned a finite loss and
   non-finite parameters without raising. Captured AMP paths now check gradients, parameters,
   optimizer tensor state, and EMA state once per epoch, after the final replay. The GPU regression test is now the
   final-step case and passes on the pinned Torch 2.2.2 environment.
2. **`speed_probe_steps` counted epochs, not steps (fixed).** The old autotuner ran one full warmup
   epoch, then called `train()` again with a new optimizer/new graph for
   `max(1, probe_steps // 4)` full epochs. Thus the advertised 8-step probe scaled with dataset
   length, included graph recapture, and caused the 78m42s electricity run. The **"auto is
   intrinsically ~5x slower" conclusion is retracted**: the corrected primitive uses one optimizer
   and graph, two untimed batches, then exactly `speed_probe_steps` timed full-size batches. It has
   been GPU-smoked (eager vs graph) but the full electricity run has not been repeated.
3. **Regression run records dropped speed provenance (fixed).** The regression branch continued
   before adding `speed_mode` / `speed_timings_s`; the old electricity-auto JSON therefore cannot
   audit its mixed modes from the record despite the narrative's claim. New regression records
   carry the same fields as classification records, with a dedicated regression test.
4. **`cuda_graph_tail` covered only standard `train()`, not DS/ACT (fixed).** In the historical
   M18e tail run, both `n_sup` arms were byte-identical to the no-tail run because the flag was
   silently ignored; only `trm_nods` recovered rows. DS/ACT now capture a second fresh/carry graph
   pair for the ragged shape on the shared pool. A real-GPU DS tail test passes. The old whole-run
   "recovers the tail" wording applies only to the standard arm.
5. **The claimed faithful electricity DS proxy was not faithful (corrected, result retracted).** It
   used a 2-wide CE classification readout instead of horizon-24 MSE, disabled the real arm's
   per-step readouts, and used batch 128 rather than the real microbatch forward size 64. The
   **2.76x slowdown / "high-channel DS question closed" conclusion is retracted**. The script now
   matches the forward/loss shape and labels itself a hypothetical stress test, but has not been
   rerun and still cannot represent the real effective-batch accumulation (graphs and microbatching
   remain incompatible). The practical high-channel DS question is open/non-actionable because no
   real regression config admits `n_sup>1`.

Finally, the main mode table below has only one tracked `*_run1.log` per mode even though
`docs/GPU_BENCHMARK.md` required two runs and retaining the second. Its 2.25x/2.11x wall-clock
ratios are therefore **provisional single-run measurements**, not repeat-validated estimates.

## 0. Provenance and scope

The M35 code (DS-family `amp`/`cuda_graph` capture, `amp`+`cuda_graph` composition,
`cuda_graph_tail`, `train.speed: auto`, per-batch sync removal, on-device eval collection —
see CLAUDE.md §11.1) arrived in this repo's working tree pre-written and CPU-correctness-tested,
but **never run on a GPU** — it was built in a CPU-only container. This narrative is the
GPU-verification pass: fix what breaks, measure what the CPU pass could only hypothesize about,
and turn §11.3's "unmeasured, treat as hypotheses" caveat into a real §11.2 entry. All runs are
on this repo's usual dev box (RTX 2070, 8GB, Turing, fp16 tensor cores only — see the global
CLAUDE.md hardware note). No scientific (§11.2 research) claim changes here — like `infra-2.md`,
this is a perf/correctness narrative, not a new milestone result.

## 1. A real bug, found by the first real GPU test run

`pytest -q` on this box: **357 passed, 1 failed** on the untouched M35 tree (up from "skipped"
on CPU, since the CUDA-marked tests finally executed for real). The failure:
`TestDeepSupervisionGraphsOnGPU::test_ds_graph_with_amp_and_ema` — `train_deep_supervision`
under `amp=True, cuda_graph=True` raised a non-finite-epoch-loss error at epoch 1.

Isolated before touching anything:
- **Not EMA-specific** — fails identically with `ema_decay=None`.
- **Not a graph-mechanics bug** — eager AMP (dynamic `GradScaler`, no capture) on the identical
  config trains cleanly for all 12 epochs, descending smoothly, no overflow.
- **It's the default static loss scale.** Binary-searched `amp_static_loss_scale` on the DS
  multi-pass path (`n_sup=3`, `carry=True`, `hidden_dim=16`, `n_steps=3`): 32768 trains cleanly
  and matches the eager trajectory; the shipped default of 65536 overflows fp16 gradients every
  time. The single-pass standard path (`test_amp_plus_cuda_graph_trains`, same 65536 default) was
  fine — this is a DS-family-specific numerical margin issue, not a universal one.

**Fix:** lowered the default `amp_static_loss_scale` from 65536.0 (GradScaler's usual init value,
never actually run on a GPU before this) to **8192.0** — an 8x margin below the observed failure
point, comfortably below the last-known-good 32768. Updated in `src/looptab/train/loop.py`
(6 call-site defaults) and `src/looptab/config.py` (`TrainConfig.amp_static_loss_scale`), plus the
CLAUDE.md §11.1 M35 paragraph. `pytest -q` after the fix: **358 passed, 6 skipped** (the 6 skips
are the pre-existing, unrelated `trm_mixer_fused` extension tests that need the MSVC toolchain —
not part of M35). The overflow-detection test itself (`amp_static_loss_scale=1e30`, deliberately
absurd) still raises correctly — the fix only moved the *safe* default, not the overflow check.

## 2. DS-family capture — the main new lever, GPU-measured

Config: `m18e_compute_matched` (converge rule=78 w=24, 3 arms × 8 seeds, `hidden_dim=64`,
`n_steps=6`; `trm_nsup`/`trm_nsup_nocarry` are the `n_sup=4` DS-family arms this lever targets),
device switched to `cuda`, `parallel_workers: 4` (kept — §11.1 says GPU workers still help; this
config is small enough that the CUDA-context-per-worker cost is proportionally larger than on
M23's sweep, so treat these wall-clock numbers as this-config-specific, not a general
`parallel_workers` re-measurement).

| mode | wall clock (8 seeds) | vs eager | Δ(trm_nsup−trm_nods) acc | Δ EM |
|---|---|---|---|---|
| eager (GPU) | 4m31s | 1.00x | +0.0211 ± 0.0054 | +0.272 ± 0.055 |
| `cuda_graph` | 2m00s | **2.25x** | +0.0232 ± 0.0067 | +0.292 ± 0.070 |
| `amp` | 5m45s | **0.78x (slower)** | +0.0231 ± 0.0044 | +0.289 ± 0.046 |
| `amp`+`cuda_graph` | 2m09s | **2.11x** | +0.0234 ± 0.0064 | +0.296 ± 0.066 |
| CPU reference (committed M18e, `m18e_compute_matched_20260625T072348`) | — | — | +0.0236 ± 0.0026 | +0.295 ± 0.023 |

All five numbers (four GPU modes + the pre-existing committed CPU run) agree well within seed
noise — genuine correctness confirmation of the new DS-family capture path, not just "ran without
crashing." Three real findings:

1. **`cuda_graph` alone is a real 2.25x win here** — the shape (`n_sup=4` passes × small cells)
   is exactly the launch-bound regime #16 predicts graphs help.
2. **`amp` alone is a real loss (0.78x)** on this shape — consistent with the repo's established
   "small GEMMs lose under AMP" pattern (§11.3: sudoku 1.18x, ETTh1 0.74x, yeast 0.65x). This
   config's GEMMs (`hidden_dim=64`, `batch=256`, `w=24` cells) are in the small-GEMM band.
   `train.speed: auto` exists precisely because this sign is not predictable from the config
   alone without measuring — see §3.
3. **`amp`+`cuda_graph` composition is real and correctly implemented**: 2m09s ≈ the `cuda_graph`
   number, not the `amp` one — the static-loss-scale capture absorbs amp's per-step host-side
   overhead into the replayed graph rather than inheriting amp's standalone GEMM-bound penalty.
   This is the first time these two knobs have run together on real hardware (they were mutually
   exclusive before M35).

`cuda_graph_tail` (same config, `cuda_graph: true, cuda_graph_tail: true`; `n_train=4000,
batch_size=256` gives a genuine 160-row ragged tail, 4% of each epoch, not the negligible case the
doc's own `_small_loader` example describes): **2m00.6s — no measurable overhead** over plain
`cuda_graph` (2m00.1s), and `trm_nods` accuracy ticked up (0.9668 vs 0.9654) in the direction
expected from training on the recovered rows. Real, cheap, and correct on an actual config, not
just the unit-test shape.

**Not run this pass:** the ACT config row (`m23_sudoku_act_sweep`, `docs/GPU_BENCHMARK.md` §2a's
bonus row) — the other two checklist items below (§2b sync removal, and the DS-family-at-scale
question) were run instead, as the higher-value follow-ups.

### DS-family capture at electricity-scale width — the definitive answer to §11.3's open hypothesis

§3b's `electricity` check exercised the *standard* path at real widths, not DS-family capture —
electricity's arms don't set `n_sup>1`, and `n_sup>1` is in fact **structurally blocked for
regression tasks entirely** (`run.py` raises: "regression ... supports only standard train
path"). So the open question from §11.3 ("DS-family graphs should hurt at electricity/traffic
scale, same memory-pool competition as #18") could not be tested via any real config — it required
a direct micro-benchmark.

Two proxies were tried. The first (`bench_dsfamily_h1110.py`: flat `TRM`, `hidden_dim=1110`, but
a synthetic `converge` task's tiny `in_features=32`) showed no OOM and no meaningful slowdown —
but this was misleading: electricity's real memory pressure comes from the **huge `M×lookback`
input layer** (321×96 = 30816 `in_features`), which the synthetic task's 32-dim input doesn't
replicate. It was also the wrong architecture — electricity's actual `h1110` arms are `TRMMixer`
(per-cell, token-mixing), not flat `TRM`; a flat dense `in_features(30816)→hidden(1110)` layer is
never built in the real recipe (exactly why the committed config keeps flat `trm`/`ff_matched` at
`hidden_dim=64`, not 1110).

**RETRACTED (see the correction block at the top, and §5a below for the corrected numbers) — the
table and conclusion in this subsection used a proxy with the wrong batch size (128 instead of the
real 64) and are WRONG. Read §5a for the real result (1.36x slower, both modes fit in 8GB), not
this subsection.** Left in place only for provenance.

The faithful version (`bench_dsfamily_h1110_mixer.py`): real `TRMMixer` class, real
`in_features=30816`, `out_features=321`, `hidden_dim=1110`, `token_hidden=8`, `n_steps=8` — with
`n_sup=4, carry=True` DS-family capture bolted on directly via `train_deep_supervision` (bypassing
`run.py`'s regression guard; labels are random since this measures architecture/shape cost, not a
training result):

| mode | per-pass time | peak GPU memory |
|---|---|---|
| eager | 7.58s | **11.37GB** (already exceeds the 8GB card — WDDM shared-memory spill) |
| `cuda_graph` (DS-family, two graphs) | 20.93s | **11.99GB** |

**Confirmed, decisively: DS-family capture at electricity-scale width is harmful, matching (and
if anything sharper than) #18's standard-path finding** — `cuda_graph` is **2.76x slower**, not
faster, and uses more memory on top of an already-overflowing eager baseline. This also explains
why the committed real recipe needs `microbatch_size=64` even in eager mode at this shape — full
`batch_size=128` eager alone already exceeds 8GB. §11.3's open hypothesis is now a closed,
measured result: never combine `cuda_graph` with a wide (`hidden_dim`~1000+), high-`in_features`
`TRMMixer`/DS-family arm — not even without the graph doubling, since eager alone is already at
the memory ceiling there.

## 3. `train.speed: auto` — correctness confirmed, reseed confirmed, one real limitation found

Ran `m18e_compute_matched` with `speed: auto`, `parallel_workers: 1` (clean per-arm timing
signal, no cross-process GPU contention).

- **Picks the right mode.** For `trm_nods` (the one standard-path arm in this config — see below
  for why the other two aren't eligible), every one of 8 seeds chose `cuda_graph`
  (`eager≈0.24s | amp≈0.30s | cuda_graph≈0.105s (best) | amp+cuda_graph≈0.12s`) — exactly the §2
  manual-sweep winner.
- **Reseed is exact, not just close.** Per-seed `trm_nods` accuracy under `auto` matches the
  manual `cuda_graph` run to 3dp on all 8 seeds (e.g. seed0: 0.966/0.966, seed7: 0.957/0.957).
  Per-seed `trm_nsup`/`trm_nsup_nocarry` accuracy under `auto` matches the manual **eager** run to
  3dp on all 8 seeds (they fall back to eager — see next point). Autotune probing genuinely does
  not leak into the real run's RNG stream.
- **Real limitation, not a bug: DS-family arms get NO autotuning under `speed: auto`.**
  `trm_nsup`/`trm_nsup_nocarry` (`n_sup=4`) are exactly the arms §2 shows benefit most from
  `cuda_graph` (2.25x), but `_autotune_speed_mode` only probes through the standard-path `train()`
  call, so any arm with `n_sup>1` / `use_act` / a curriculum / `train_stable` falls straight
  through to the configured flags — here, the config's defaults (`amp=False, cuda_graph=False`),
  i.e. **plain eager**, silently. The run record labels this honestly
  (`speed_mode: "eager (auto n/a here)"`), so it's discoverable, but it means **on a config whose
  interesting arms are DS-family, `speed: auto` currently buys nothing** — the exact opposite of
  what someone reaching for "the main new lever" would expect. Worth a CLAUDE.md callout (added
  below) so nobody assumes `speed: auto` covers the DS-family win automatically.

### 3b. `speed: auto` at real scale (`electricity`, M=321) — correct, but the probe overhead can dominate

Ran the committed `m34_electricity_h24` config (7 arms, 4 seeds, widths up to `hidden_dim=1110`)

`n_sup` multi-pass DS-family routine — so that specific §11.3-hypothesis (a) claim remains

The other five arms (`hidden_dim` 44–340) *were* auto-probed, and the autotuner behaved sensibly:
it never picked plain `cuda_graph` for the two `h340` arms (probed timings show it losing to

`cuda_graph`/`amp+cuda_graph` — the small/launch-bound regime §16 predicts. No candidate ever
registered as unavailable/OOM at these widths (the true #18 danger zone, `h1110`, was never
exposed to the autotuner by design).

full epochs instead of `speed_probe_steps` batches; (2) separately, the "~16 minutes" baseline
below was a misread per-seed figure, not a 4-seed total.** The paragraph below is left for

~~But wall clock was 78m42s vs. ~16 minutes for the original recipe — roughly 5x SLOWER

## 4. Net assessment (superseded by the correction block above, and by §5 below)

What remains defensible after review:

- DS-family graph capture and AMP+graph composition pass real-GPU convergence tests. The measured
  2.25x/2.11x small-config speedups are promising but **provisional until the required second
  timing run exists**.
- Static AMP now has final-step post-update gradient/state validation; lowering the default scale alone was
  not sufficient protection.
- Tail capture now covers standard, DS, and ACT paths. The historical M18e timing measured tail
  recovery only on its standard arm; the DS implementation is GPU-unit-tested but not full-run
  timed.
- The ~3% sync-removal A/B remains a scoped, bit-identical plumbing result.
- `speed:auto`'s step-count/setup bug and regression-provenance omission are fixed. Its standard-
  path choices need rebenchmarking under the corrected bounded probe; DS-family arms remain outside
  autotuning and are honestly labelled as such.
- The electricity-shaped DS result is **withdrawn**. The corrected script is a hypothetical stress
  test only and has not been rerun; it cannot close a question about a real training configuration
  that the runner does not support.

Not yet done: the `m23_sudoku_act_sweep` ACT row (low priority — #16 already established
`cuda_graph` is inert at sudoku's compute-bound scale, so this would mostly be a completeness
check on the ACT-specific halt-loss capture path, not a new speed finding).

## 5. Follow-up (this pass): closing the items the review left retracted or provisional

All five of Codex's fixes were verified independently on this box (not just trusted): full suite
**362 passed, 6 skipped** (up from 358 — the four new regression tests all pass for real on this
GPU, including the two `cuda_graph_tail`-on-DS/ACT tests). Then the retracted/provisional items
were closed one by one.

### 5a. The corrected electricity-shaped DS proxy — a much smaller effect than the retracted 2.76x

Reran `bench_dsfamily_h1110_mixer.py` after its correction (real horizon-24 MSE readout, per-step
deep-supervision losses enabled, batch=64 matching the real arm's microbatch forward size, instead
of the withdrawn CE/batch-128/no-DS version):

| mode | per-pass time | peak alloc | peak reserved |
|---|---|---|---|
| eager | 569ms | 5.77GB | 5.94GB |
| `cuda_graph` (DS-family) | 775ms | 6.13GB | 6.74GB |

**Corrected finding: `cuda_graph` is 1.36x slower (not the retracted 2.76x), and both modes fit
comfortably inside the 8GB card (not the retracted "eager alone already exceeds 8GB").** The wrong
batch size in the withdrawn proxy (128 vs. the real 64) was the dominant driver of both errors —
doubling the batch roughly doubled memory and pushed the false OOM reading. This remains a
**hypothetical stress test, not a real-workload result**: `n_sup>1` is structurally blocked for
regression tasks, and even where it weren't, `cuda_graph` and `microbatch_size` (true gradient
accumulation) are mutually exclusive, so this probe's "batch=64" is a stand-in for the real arm's
microbatch forward shape, not an accurate simulation of accumulation semantics. Net: DS-family
capture at electricity-scale width is a **modest, unremarkable loss** (not a catastrophic one) —
still not worth turning on, but the earlier "decisively confirmed harmful" language overstated it.

### 5b. `speed:auto` at real scale, rerun with the fixed bounded probe — plus a second error, this one mine

Reran `m34_electricity_h24` with `speed: auto` under the corrected probe: **64m30s total**, barely
different from the withdrawn buggy run's 78m42s. At first glance that looked like the fix hadn't
helped much. It had — the per-candidate probe cost dropped roughly 14x (individual candidate
timings are now sub-2s instead of 14–33s, confirmed in the run's `[speed:auto]` log lines) — but
**the "~16 minutes" this was being compared against was itself wrong**. That figure, carried
verbatim from CLAUDE.md's M34 entry ("electricity's single-seed wall-clock went from 2+ hours to
~16 minutes"), is a **per-seed** number, and this run's own wording ("78m42s vs. ~16 minutes for
the original recipe") silently compared it against a 4-seed total — an error introduced in the
original M35 pass, not by Codex's review, and not caught until this follow-up.

Directly timed the actual committed baseline (`configs/experiments/m34_electricity_h24.yaml`, no
auto, 4 seeds, freshly run rather than assumed): **64m53.9s** — statistically indistinguishable
from the fixed-probe auto run's 64m30s. **Once the probe bug is fixed, `speed: auto` is NOT
meaningfully slower than manual pinning at this scale.** Both the original "~5x slower" claim
(Codex's retraction, correct) and this pass's initial reading of "still ~4x slower" (this
follow-up's own error, now also corrected) do not survive contact with a properly-measured
baseline. Headline Δs still reproduce (checked against the fresh baseline run, not the old one):
Δ(trm_mixer−ff_matched) accuracy +0.1197±0.0269 (baseline) vs. +0.1219±0.0248 (auto);
Δ(trm_flat−ff_matched) +0.0307±0.0229 vs. +0.0321±0.0217 — both within noise.

One targeted follow-up to make sure this wasn't two errors cancelling out: timed real (not probed)
15-epoch training for a single representative auto-eligible arm (`trm_mixer_unsharedro`, h340, 1
seed) across all four modes directly, to check whether any mode's *sustained* cost diverges badly
from what the short probe predicts:

| mode | 15-epoch wall clock (1 seed) |
|---|---|
| eager | 158.8s |
| `cuda_graph` | 154.3s |
| `amp` | 115.5s |
| `amp`+`cuda_graph` | 110.4s |

No divergence — `amp`+`cuda_graph` (the autotuner's pick for this arm) is genuinely the fastest at
full sustained scale too, consistent with the 8-batch probe's read. The probe's choices are sound;
the earlier confusion was purely the baseline-comparison error above, not a probe-fidelity gap.

### 5c. `cuda_graph_tail` on DS-family arms, rerun with the fix

Reran `m18e_cuda_graph_tail` (same config as §2, `cuda_graph: true, cuda_graph_tail: true`).
Before Codex's fix, `trm_nsup`/`trm_nsup_nocarry` were silently byte-identical to the no-tail run
(the flag was ignored on the DS path) — only `trm_nods` actually recovered the dropped rows, a gap

`trm_nods`'s already-correct behavior. Wall clock: 2m08.5s, same negligible overhead as before.

### 5d. 2a table: repeat runs, provisional → repeat-validated

Reran `eager` and `cuda_graph` a second time each (`docs/GPU_BENCHMARK.md`'s own two-run
protocol). Both modes are deterministic without AMP, so the repeats reproduced **bit-identically**:
eager 4m29.7s (run1: 4m30.9s) with byte-identical Δs; `cuda_graph` 2m00.1s (run1: 2m00.1s) with
byte-identical Δs. The 2.25x ratio is now repeat-validated, not provisional. `amp` and

agreement with the CPU reference and with each other in §2 is already independent corroborating
evidence, unlike the DS-proxy and `speed:auto` items above where the single-run numbers were

### Net effect of this follow-up

Two of Codex's five "fixed, not yet rerun" items now have real, verified numbers (5a, 5c); the
third (`speed:auto` at scale) was rerun and turned up a second, independent error in the *original*
comparison baseline — now corrected. Revised bottom line: **DS-family capture, AMP+graph
composition, and `cuda_graph_tail` are all real, GPU-verified wins with no outstanding surprises**;
